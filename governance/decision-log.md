### 2026-09-20 — The CTO held the gate's own hardening commit, then authored the fix: five more bypasses closed
- **Decision:** `8a99ecb` ("Harden the push gate…") was **HELD**, not approved, by the `cto`, and the fix was authored by the `cto` in a follow-up commit rather than by the CEO session. The hold is recorded in `workspaces/engineering/work/2026-09-20-cto-push-gate-review.md`; the record `governance/approvals/2026-09-20-push-gate-hardening.md` is **superseded audit trail and must never be reused**.
- **What the review found, and what the fix closes.** Five ways to get a push past the gate, each now closed and each with a regression test that was demonstrated failing against `8a99ecb` (see `workspaces/engineering/work/2026-09-20-cto-push-gate-fix.md` for the two test runs): (1) **`refs/replace/*`** — every git read in the checker honoured replace refs, which `git push` does not, so `git replace <evil> <benign>` made the gate inspect a different history from the one being transferred; all git calls now use `--no-replace-objects`, and so does the hook. (2) **Add-then-remove** — the checker compared two end points, so a file committed and deleted in the next commit was invisible; it now walks **every commit** in `approved..tip` and refuses a merge or root commit in that range. This is the ordinary way a credential reaches a remote (firm rule 5). (3) **Submodules** — `diff.ignoreSubmodules=all` or `ignore = all` in `.gitmodules` hid a repointed gitlink; diffs now pass `--ignore-submodules=none` and `-c diff.ignoreSubmodules=none`. (4) **Quoted front-matter keys** — `"cto_decision": HELD` followed by `cto_decision: APPROVED` defeated the duplicate-key guard; quoted keys are now refused. (5) **Path shape** — `governance/approvals/` was a string prefix test, so a tree entry named `..` or `.git` kept the prefix and the `.md` suffix while writing outside the directory; those components are refused. Also fixed: a non-ASCII record filename was C-quoted by `ls-tree` and became invisible (it failed closed, but it failed). The "Honest limits" docstring, which did not mention any of this, was rewritten to be true and now names what remains open — a forged record, a hostile clone (including `.git/info/grafts`, which `--no-replace-objects` does **not** disable), `--no-verify`, a clone without the hook, GitHub API clients, and remote movement after the hook runs.
- **Why the hold rather than approve-then-fix:** the push itself was materially safe (verified: no replace refs, no submodules, no add-then-remove in that range), but a control whose own file misstates its limits gets trusted further than it deserves, and the next push would have relied on the two-point diff. The fix cost one QA cycle — the same cycle it would have needed later — and saved a push cycle.
- **Two boundary exceptions, recorded rather than left silent:** (1) `workspaces/registry.json` gives `scripts/**` to the `cto` alone and `tests/**` to `cto`/`qa-tester`, yet the **CEO session authored** those files in `8079c73` and `8a99ecb` — a real violation, not a false positive. Remedy: the `cto` authored this fix, owns that code from here, and `check_boundaries.py --role <git author>` cannot attribute authorship in this firm (every agent commits as the same local git user), so **the authoritative author is the role named in the push-approval record**. (2) This fix commit also touches `governance/policies/push-checklist.md`, `governance/templates/push-approval.md`, `governance/decision-log.md`, `HANDOFF.md` and `docs/backtest-bot/status-and-roadmap.md`, which the registry does **not** give to the `cto`. Written on the CEO's explicit work order, because the wording in those files stated something the code does not do (only added or modified regular `*.md` files under `governance/approvals/` are allowed, not "anything under `governance/approvals/**`") and the test counts had changed. The CEO owns that wording; the CTO owns the code it describes.
- **Still open, for the founder:** the record template says an author "must not be the signer of sections 2 or 3", but `scripts/**` is cto-only, so the CTO must author gate fixes **and** signs section 3. Proposed wording: "must not be the QA signer", with the CTO-as-author case named as an exception. Left unchanged pending the founder; the compensating control is QA's adversarial fresh-clone verification.
- **Measured after the fix** (this working tree, pending QA's fresh-clone re-verification): bot **55 passed / 6 failed**, org tooling **43 / 8** (both unchanged), push gate **63 / 0** (12 new tests; 11 of them fail against `8a99ecb`, 7 of those because the old script **allowed** the push).
- **Approved by:** CTO (author and holder) → pending QA re-verification → CEO. **No push is approved by this entry.**
- **Record:** superseded: `governance/approvals/2026-09-20-push-gate-hardening.md`. A new record will be written for the fix commit.
- **What would reverse this:** GitHub branch protection being enabled, which would make the local hook a convenience rather than the control — the per-commit walk and the replace-ref flag would still be worth keeping, but the firm would stop depending on them. Or a finding that the per-commit walk is too slow on a long approved range (it is one `git diff` per commit; not observed at this repository's size).

### 2026-09-20 — The push gate's first verification failed; hardened it, and stopped using stand-in agents
- **What happened.** The gate's first run was a QA verification of commit `8079c73` from a fresh clone. Verdict **FAIL** — QA found a working bypass and two further holes in `scripts/check_push_approval.py`: (1) `git diff` with rename detection reported *delete `src/x.py` + add `governance/approvals/x.txt`* as one harmless rename into the exempt directory, so any code, including `risk/` or `execution/`, could be deleted or neutered after QA verified it — QA demonstrated it landing on a remote; (2) a force-push with a fresh valid record was allowed, because the hook ignored the remote's current commit; (3) duplicate front-matter keys were accepted with last-one-wins, so `cto_decision: HELD` followed by `APPROVED` passed. All three documented as fixed below. The 33 original tests had no case for any of them.
- **Fixes.** The post-approval comparison now runs with rename detection **off** and allows only added or modified regular `*.md` files under `governance/approvals/` (deletions, renames, symlinks, other extensions and mode changes are refused); duplicate keys make a record invalid; the hook reads the remote's SHA and refuses anything that is not a fast-forward, or a remote tip the clone has not fetched. 18 regression tests were added (51 total, all passing). **These fixes have not yet been re-verified by QA.** Two lower-severity observations remain by design and are stated in the script: any `*push*.md` under `governance/approvals/` counts as a record and one valid record suffices, and nothing verifies *who* wrote a record.
- **The stand-in problem, and the decision.** QA's verification was performed by a **general-purpose agent given the `qa-tester` role**, because the named `qa-tester` and `cto` agents were not loadable: project agents in `.claude/agents/` are registered when a session starts in the repository root, and this session started elsewhere (confirmed by calling `qa-tester` by name: *Agent type not found*; changing directory mid-session does not reload the list). The founder asked why the real agent was not called. **Decision: a record signed by a stand-in is not accepted as the QA or CTO signature. The gate is re-run, from the top, by a session started in the repository root, with the real `qa-tester` and `cto`.** The stand-in's report is kept only as evidence of the three findings. The earlier entry's sentence that the stand-ins would sign this push's records is superseded by this decision.
- **What this shows about the process.** The first real use caught a bypass in the gate's own code — the author's own tests had not. That is the argument for the rule.
- **Approved by:** Founder (asked the question that exposed the stand-in) → CEO
- **What would reverse this:** Named agents becoming loadable regardless of launch directory, which would remove the need for a session restart.

### 2026-09-20 — No push to GitHub without QA's fresh-clone verification and the CTO's approval (the push gate)
- **Decision:** Every push to the remote — any size, any branch, docs included — requires a **push-approval record** signed by `qa-tester` (verified from a **fresh clone** of the exact commit) and by the `cto` (approved only after reading QA's evidence). Added as **gate 5** in `governance/approval-policy.md`. The checklist of what must be updated and reviewed before every push is `governance/policies/push-checklist.md`; the record template is `governance/templates/push-approval.md`; the CTO, QA and CEO agent definitions, `CLAUDE.md`, `.claude/foundation.md`, `HANDOFF.md` §13, the deployment-approval template and the build-and-release workflow all reference it. A `/prepush` slash command runs the process.
- **Enforcement, and its limits.** `.githooks/pre-push` calls `scripts/check_push_approval.py`, which refuses a push unless the tip commit's own tree holds a well-formed record whose `approved_commit` is an ancestor of the tip, with **no changes after it outside `governance/approvals/`**, QA `PASS`/`PASS WITH NOTED RISK`, CTO `APPROVED`, and the right branch and remote. It fails closed (missing or malformed record, ref deletion, tag push, no Python) and has **no override flag**. 33 tests cover it, and it was exercised for real against a local bare remote: blocked with no record, allowed with one, blocked again after a change slipped in behind QA. **It is local:** `git push --no-verify`, a clone without the hook (`git config core.hooksPath .githooks`), and pushes through the GitHub connector's API tools bypass it. **Branch protection on GitHub — require a pull request and a passing check — is the only complete control; it is a founder-side setting and is not yet enabled.** The rule also depends on agents not forging a signer's lines; `check_boundaries.py` and the CTO's review are the check on that.
- **Rationale:** Founder's instruction: the CTO must be aware of, and must follow, a pre-push checklist, and nothing may reach GitHub without the CTO's approval after the CTO confirms with the tester. The concrete failure behind the fresh-clone requirement: the OHLCV loader was never committed because a `.gitignore` rule hid it, and the previous "fresh clone" check ran in a directory that still contained the files. A check that runs where the code was written proves little about what is in the repository.
- **Applied to this push.** The founder's direct instruction to push, and the rule they set in the same message, were both honoured: the gate was run on the push that introduced it. The named agents `cto` and `qa-tester` are not loadable from a session started outside the repository root, so they were dispatched as general-purpose agents given their definitions from `.claude/agents/`; the records say so.
- **Boundary note:** `scripts/check_push_approval.py`, `.githooks/pre-push` and `tests/test_push_gate.py` are CTO-owned paths written here by the CEO at the founder's direction and submitted for the CTO's review as part of the very approval they enforce. `workspaces/registry.json` gained a rule for `.githooks/**` (CTO). `.gitattributes` pins the hook to LF so a Windows checkout does not break it.
- **Alternatives considered:** Instruction-only (rejected — a rule nothing checks is the failure this firm has already had once); a Claude Code `PreToolUse` hook (rejected as the primary control — it covers only Claude sessions, whereas a git hook covers any `git push` from a clone that installs it); requiring the founder to approve every push (rejected — the founder asked for the CTO to be the approver); approving the tip commit directly (impossible — a record cannot contain the hash of the commit that contains it, hence the two-commit shape).
- **Approved by:** Founder (directed it) → CEO
- **What would reverse this:** Server-side branch protection with required review and checks on GitHub making the local gate redundant — at which point the CTO's approval becomes a required review and this hook becomes a convenience.

### 2026-09-13 — EMA crossover strategy spec approved; one year of 1h data cannot prove an edge
